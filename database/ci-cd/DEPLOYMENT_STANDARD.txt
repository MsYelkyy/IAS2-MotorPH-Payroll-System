PURPOSE
-------
This document is the single source of truth for how the database reporting
layer is built and validated. It covers two paths:

  A. MANUAL build/validate    -- run by a person in MySQL Workbench (or the CLI)
  B. AUTOMATED validation     -- run by the Database Report CI/CD Pipeline on
                                 GitHub Actions

Scope note (honest): this is a DATABASE REPORT CI/CD pipeline. It rebuilds and
validates the database reporting layer in a clean MySQL environment. It is NOT a
production deployment pipeline -- it does not deploy to, or otherwise touch, any
live/production database or server. "Deploy" here means "stand up the reporting
layer on a fresh test database", nothing more.


PREREQUISITES
-------------
  * MySQL 8.x (developed/tested on MySQL 8.0).
  * Character set utf8mb4 (the dump sets this; the CI client uses
    --default-character-set=utf8mb4).
  * A MySQL account able to CREATE DATABASE, CREATE VIEW, and read all tables.
  * Files in place (actual relative layout):
        database/payrollsystem_db.sql  -- the project database dump (lives at the
                                          database/ root, NOT inside sql_scripts)
        database/sql_scripts/          -- the report + test SQL scripts
        database/ci-cd/                -- deploy_reports.sql, run_all_tests.sql,
                                          this document
  * The project database dump is:  database/payrollsystem_db.sql
    (This is the canonical dump for the project. deploy_reports.sql references
     it as ../payrollsystem_db.sql relative to database/ci-cd/.)


DEPLOYMENT FILES (database/ci-cd/)
----------------------------------
  deploy_reports.sql      -- builds the reporting layer in the correct order
  run_all_tests.sql       -- runs all validation + supporting test scripts
  DEPLOYMENT_STANDARD.txt -- this document


RUN ORDER (and why it matters)
------------------------------
deploy_reports.sql runs these in order; each step depends on the ones before.
Paths are relative to database/ci-cd/ (where the script is run from):

  1. ../payrollsystem_db.sql
        Schema + data. Creates payrollsystem_db and all tables.

  2. ../sql_scripts/seed_payroll_earning.sql
        REQUIRED. The dump ships the payroll_earning table EMPTY, so this seed
        back-fills the BASIC_PAY earning rows. Without it, basic_pay shows 0.00
        in the report views and the reconciliation tests fail.

  3. ../sql_scripts/employee_payslip_report_view.sql
        Creates vw_employee_payslip_report (per-payslip report).

  4. ../sql_scripts/payroll_summary_monthly_view.sql
        Creates vw_payroll_summary_monthly (monthly summary report). Both views
        must exist before the tests run, because the tests read from them.


-----------------------------------------------------------------------------
A. MANUAL BUILD / VALIDATE (MySQL Workbench or CLI)
-----------------------------------------------------------------------------
Because SOURCE resolves paths from the client's current folder, open the
scripts from the database/ci-cd/ folder OR adjust the relative paths.

Option 1 -- run the deploy script:
  1. Open MySQL Workbench and connect to your local MySQL 8 server.
  2. Set the working folder to database/ci-cd/ (or open deploy_reports.sql from
     there), then run:
         SOURCE deploy_reports.sql;
     This rebuilds the schema + data, seeds BASIC_PAY, and creates both views.
  3. To run all tests, then run:
         SOURCE run_all_tests.sql;
     Read the result grids: every row ends in PASS or FAIL, and each suite prints
     a final verdict line.

Option 2 -- run the individual scripts (in the run order above) if you prefer to
  step through them one at a time.

Command-line equivalent (from database/ci-cd/):
    mysql -u root -p --default-character-set=utf8mb4 < deploy_reports.sql
    mysql -u root -p --default-character-set=utf8mb4 --table < run_all_tests.sql


-----------------------------------------------------------------------------
B. AUTOMATED VALIDATION (GitHub Actions)
-----------------------------------------------------------------------------
Workflow file: .github/workflows/database-report-ci.yml
Triggers:      push, pull_request, and manual workflow_dispatch.

What each run does:
  1. Starts a clean, throwaway MySQL 8 service container (empty database).
  2. Runs database/ci-cd/deploy_reports.sql
        -> rebuilds schema + data + views from scratch.
  3. Runs database/ci-cd/run_all_tests.sql
        -> executes all validation + supporting tests, capturing the full
           output to test_output.log.
  4. Pass/fail gate (shell-level). The workflow scans test_output.log for a
     REAL failure and fails the build if it finds one:
         * a FAIL result cell in a table grid  (matched as "| FAIL |"), OR
         * a "TEST(S) FAILED" verdict line.
     It deliberately does NOT match on the bare word "FAIL", because a PASSING
     run still prints:
         * the lowercase "failed" column header, and
         * one scenario label that literally contains FAIL
           ("...run seed_payroll_earning.sql if FAIL").
     Neither of those is a failure, so they must not trip the gate.
  5. Uploads test_output.log as a downloadable artifact
     (name: database-report-test-output) -- kept even when the build fails, so
     the evidence is always available.

This pipeline does NOT build or test the Java application. It never runs Maven
and never touches src/main/java, src/main/resources, pom.xml, or target/.

Why this is meaningful evidence:
  Every run proves the reporting layer can be rebuilt from nothing on a clean
  MySQL 8 database and that all report validation tests pass against it.


IDEMPOTENCY / RE-RUN NOTES
--------------------------
The build is safe to re-run and returns the database to a known-good state:
  * payrollsystem_db.sql uses CREATE DATABASE IF NOT EXISTS and DROP TABLE IF
    EXISTS, so re-running rebuilds the schema cleanly.
  * Both report views use DROP VIEW IF EXISTS + CREATE VIEW, so they refresh on
    every run.
  * The BASIC_PAY seed is written to be safe to re-apply.
  * The test scripts write only TEMPORARY tables (dropped at session end) and do
    not modify business data, so re-running tests has no side effects.


ROLLBACK
--------
  * Test runs: nothing to roll back -- tests are read-only (TEMPORARY tables
    only), so no business data changes.
  * Manual build: re-running deploy_reports.sql rebuilds the database to the
    known-good state defined by payrollsystem_db.sql, which effectively rolls
    back any local drift. To fully reset, drop the database
    (DROP DATABASE payrollsystem_db;) and re-run deploy_reports.sql.
  * CI runs: the MySQL container is thrown away after every run, so there is no
    state to roll back -- each run starts clean.
